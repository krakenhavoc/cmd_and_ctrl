# Snapshot compatibility (#522)

The rules are summarised in [AGENTS.md](../AGENTS.md) §5. This file has the detail.

A restore point written by yesterday's binary has to restore in today's. Three tests hold that line, and the rule they enforce is written next to `SnapshotSchemaVersion` in `server/internal/game/snapshot.go`: changes within a version are additive only, anything else is a bump, and fixtures are never edited.

- **The shape guard.** `TestSnapshotShapeIsRecorded` (`internal/game`) compares the snapshot structs' JSON shape with `internal/game/testdata/snapshot_shape/v<N>.txt`. If you add a snapshot field, record it in the same change: `cd server && go test ./internal/game -run TestSnapshotShapeIsRecorded -args -update-shape`. The tool refuses a non-additive change (a key renamed, removed or retyped) under the current number. Bump `SnapshotSchemaVersion`, say why in its comment, and rerun it. It writes `v<N+1>.txt` and leaves the old file frozen.
- **The fixture corpus.** `TestSnapshotCorpusRestores` (`internal/cards/effects`, because restoring tokens, Clones and Equipment needs the real catalog) restores every file under `internal/game/testdata/snapshots/` with `RestoreStrict`. It fails if any key or value in a fixture is missing from a fresh capture of the restored game, if a card comes back with fewer catalog abilities than the file recorded, or if the game will not round-trip or take an action.
  - `v<N>/` is the generated set for schema N. It is written once, when N is introduced: `cd server && go test ./internal/cards/effects -run TestWriteSnapshotCorpus -args -write-corpus`. The writer never touches an existing **file** (ADR 0041 phase 3, owner decision 6): a board with no file yet is written beside the others, so a shape that becomes a restore point after its version was introduced can still be frozen without a bump. It fails unless every existing fixture is a subset of a fresh render of its board (the restore guard's own comparison, so keys added later in the version are fine and a key lost, retyped or changed is not), and tells you to bump instead (#1801). `TestSnapshotCorpusBoardsStillMatchTheirFixtures` runs that check on every CI run, and also fails on a registered board with no fixture yet. CI fails if the current version has no directory.
  - `real/` holds scrubbed restore points from cmd-dev. Add one with `cd server && go run ./cmd/snapshotscrub -in <restore/id.json> -out internal/game/testdata/snapshots/real/<name>.json`. The tool replaces names and player IDs, drops Discord IDs and avatar hashes, and refuses to write if a snowflake, an email or an original player name is left anywhere. It never overwrites a file.
  - **Never edit, regenerate or delete a fixture to make the test pass.** If a bump migrates an old shape, list the migrated paths in `corpusMigrations` in `snapshot_corpus_test.go`, with the reason. Nothing else may excuse a difference.
- **The ability check.** A card whose catalog entry lost abilities between the writing and the reading binary is restored anyway. It is flagged `Card.AbilitiesLostOnRestore`, which shows it as `manual` for the rest of the game, and the boot log has an ERROR line naming the game, the card and the counts. More abilities than captured is not a mismatch.
- **Effect keys (#1497, [ADR 0041](decisions/0041-game-persistence.md) phase 3).** A `ScopedEffect` mod kind is an on-disk identity, like a token slug: never renamed, never reused. A restore point naming a kind (or a delayed-trigger / stack-item effect key) this binary cannot interpret is refused with `ErrUnknownEffectKey` and the file is KEPT — only a newer build can have written it, so it is the rollback case. That refusal is what lets the vocabulary grow within a schema version.
- **Abilities on the stack (#1497, ADR 0041 P9, tier 4).** An ability's stack item names the catalog row it came from: `Body: "catalog/activated"` or `"catalog/triggered"`, plus `Params.Ability`, an `AbilityRef` of `{key, slot, ref, name}`. The `ref` is ADR 0093's `own:<i>` or `grant:<bundle>:<i>:<n>`, and `name` is the row's label (an activated row's `Label`, a triggered row's `Key`). `ActivateCatalogAbility` stamps every catalog activated ability. The trigger harvest stamps a triggered row that DECLARES its `Effect` (slice 4-2): the registry gives each row its identity as it files the definition (`game.IdentifyCatalogRows`), so no card file names its own row. A table with either waiting — queued or on the stack — is a restore point. Restore rebuilds the item's effect, target clause and mode clause from that row, in the running binary; a `TargetsFrom` clause is built again from the item's carried `Trigger` and its source. Three outcomes, set by the owner's answers of 2026-09-25:
  - The row at the ref has the same label: restored.
  - It does not, and exactly one row in the same list has that label (a deploy reordered the card's abilities): that row is used and the ref is rewritten.
  - No row, or more than one, has the label: the game is restored anyway. The item stays on the stack as a manual item with no effect, like a sandbox-announced one. Its source card is flagged `Card.AbilitiesLostOnRestore`, and the boot log has one ERROR line naming the game, the card, the label and the ref (`GameSnapshot.LostStackAbilities`). Never abandon the game and never drop the item.

  A binary from before slice 4-2 does not register `catalog/triggered`, so it refuses a file that names it (the rollback case). An ability carried on a card instance (`Card.ActivatedAbilities`) is never stamped and is still counted by the census. Neither is a trigger whose row computes its effect in a hand-written `Build` with no `Effect` beside it, nor one whose `TargetsFrom` reads the board (`TriggeredAbility.TargetsFromReadsBoard`): such rows would be listed in `server/internal/cards/effects/testdata/legacy_trigger_builds.txt`, which is EMPTY since tier 4-final and which `TestLegacyTriggerBuildsOnlyShrink` holds to shrinking — it fails on a listed row that no longer needs listing (delete the line, or run `cd server && go test ./internal/cards/effects -run TestLegacyTriggerBuildsOnlyShrink -args -update-legacy-triggers`, which never adds one) and on a new hand-written `Build` that is not listed (declare the `Effect` instead). A `Build` that makes a keyed item (`game.NewKeyedTriggeredItem` over a tier-2 body, as suspend and madness do) is data already and is not listed. Since this change, every stack-item field (on the stack, queued, or in `lastKnownStack`) is refused if this binary does not know it, for a file of the current schema. So a new stack-item field is refused by every binary from here on and needs no bump. `lastKnownStack`, the CR 608.2h record of spells countered this turn, is carried too. The census counts a stack item once, in `IntrinsicAbilityCards`, when its effect is a closure with no `Body` or when it has a target or mode clause with neither an oracle ID nor an ability ref behind it. In production the only such item is an ability carried on a card instance, which is that counter's own subject; a test that hand-builds an item (`newTriggeredItemForTest` in `internal/game`) lands there too. `StackTargetSpecs` and `StackEffects` are both retired (tier 4-final, owner decision 2026-09-25): `game.NewTriggeredItem(source, label)` takes no effect, because what a stack item does is always a catalog row or a registered body.
- **The resolving slot (#4270, [ADR 0041](decisions/0041-game-persistence.md) amendment of 2026-10-24).** `Game.resolving` is the stack item whose resolution is in flight, plus the card a spell was, and it is carried as `GameSnapshot.Resolving`: plain data, additive in v9, absent when empty. A keyed prompt (a pay-unless, a confirm, a `ThenKey` choice) holds no resume frame, so a table waiting on one is a restore point and its answer can read the slot (Wandering Archaic's "copy that spell?" copies the spell that already resolved). The slot lives for one event batch, restored or live: `beginEventBatchLocked` clears it, and `eventBatch` is carried. While the resolution is still open (`resolutionOpen`, a prompt paused inside it), capture counts the item and the card in the live census, as it counts a stack item and a last-known spell: one restore could not rebuild (an unkeyed Effect, a card whose instance abilities can't be re-derived) is `IntrinsicAbilityCards`, so the table is not a restore point (#4361). Once the resolution has closed, the slot is spent and capture reads it through a throwaway census. A field is `dropped` in `snapshot_drift_test.go` only when whatever pauses its prompt carries a frame; ask again when one of those prompts is keyed.
- **The asking item, named objects, a tap clause and a per-object offer (#4264, [ADR 0041](decisions/0041-game-persistence.md) amendment of 2026-10-24).** A keyed pay-unless, may-pay, upkeep, counter-unless-pays or any-player prompt carries the stack item that asked it as plain data (`pendingChoices[].asked`: controller, owner, source card, the source object with its epoch, the label, targets, triggering event, X and modes), named objects with their epochs (`optionObjects`), a waterbend clause as its kind and extra cost (`payTap`, rebuilt by `game.RegisterTapCost`; the ledger kind is `tapcost`) and, on a per-object offer, the objects, the picks so far and the noun (`anyPlayerOffer.objects`, `.picks`, `.noun`). All are additive in v9 and absent when empty; none is a route to a func.
- **A keyed "you may pay {X}" (#4289, [ADR 0041](decisions/0041-game-persistence.md) amendment of 2026-10-24).** The "choose X" prompt of Flameblast Dragon, Leyline Tyrant and Tilonalli's Summoner carries no frame, so it is written: `pendingChoices[].payAmount` (its bounds, goal and unit), `.mayPayX` (the cost, label and words of the payment that follows) and, on that payment, `.pickNumber` (the X its branches are handed). All are additive in v9 and absent when empty. `PayAmount` is `carried` in `snapshot_drift_test.go`; a `pay_amount` that still carries a `chooseValueResume` frame is counted and not written. The fixed energy payments are the existing keyed pay-unless and add no field.
- **A keyed number prompt (#4294, [ADR 0041](decisions/0041-game-persistence.md) amendment of 2026-10-24, [ADR 0129](decisions/0129-energy-getting-and-paying-it.md)).** A `pay_amount` whose `pickThen` is a `game.RegisterNumberThen` key (Harnessed Lightning's "pay any amount of {E}", Volcano Hellion's chosen damage, Necrodominance's life, Glissa Sunslayer's counters, a split of "tapped and attacking" tokens, an assist helper's share) holds no frame, so it is written, and its answer is the registered branch handed the number and the prompt's data: `pendingChoices[].pickWords`, `.pickNums`, `.attackSplit` and `.assist`, with `optionCarry`, `asked` and the cause. All additive in v9 and absent when empty. `AssistPrompt` and `CastSpellParams` are in the recorded shape: a new cast parameter fails `TestSnapshotShapeIsRecorded` until it is recorded, because an unrecorded one would be dropped by a restore. A restore refuses a number branch or a tail this binary does not have. A myriad split (the groups a token creation's replacements left, the one being split and the ones placed, `attackSplit.settled`, with its own number key `token/settled-split`) and Calamity's pick (`pendingChoices[].pickNums` and `asked` on a keyed card pick) are data too, since the amendment of 2026-10-26 (#4294); nothing in the number-answer family is a closure but a test's.
- **A keyed card-name prompt, choose-a-source prompt, land-mana walk and draw tail (#4253 slice 10c, [ADR 0013](decisions/0013-replacement-effects.md) amendment of 2026-10-26).** A resolution-time "choose a card name" (Demonic Consultation, Tamiyo) holds a registered tail (`pendingChoices[].nameThen`, its key on `pickThen`), told the name as its word. A `choose_source` prompt is a keyed `choose_cards` pick (`pickThen` is a `game.RegisterChooseSourceThen` key); the engine's own `choose-source/shield` continuation carries the shield, redirection or multiplier as `pendingChoices[].sourceShield`. The walk over a player's lands is the option pick that asks about the current one, with the lands still to visit in `optionCarry`, `pickNums` and `pickWords` (no new field). A draw-instead body's `done` is `GameSnapshot.parkedDraws`: the drawing player, the draws still owed and the instruction's then by key, by the ID the body's prompt carries. All additive in v9 and absent when empty. A restore refuses a tail, a choose key or a shield follow-up body this binary does not have.
- **A keyed colour or creature-type prompt (#4253, the sweep's second pass).** A resolution-time "choose a color" (`ChooseColorTail`: Wash Out, Oona, Selective Obliteration, Mother of Runes) or "choose a creature type" (`ChooseCreatureTypeTail`: Kindred Dominance, Patriarch's Bidding, Artificial Evolution) holds a registered tail in the same `pendingChoices[].nameThen` the card-name prompt writes, its key on `pickThen`, told the colour or the type as its word (`""` when a creature-type chooser left). No new field: `nameThen` is now written for the `color` and `creature_type` kinds too, which is additive within v9, and an older binary refuses the file because it does not know the key. A prompt still holding a `chooseValueResume` closure is counted in the census as before.
- **The closure ratchet.** `TestClosureFieldsReachableFromGame` (`internal/game`) lists every ROUTE from `Game` to something that can hold a func or an interface — every field of every reachable struct whose type reaches one, directly or through another struct — in `internal/game/testdata/closure_fields.txt`, each classified `rebuilt`, `keyed`, `transient`, `test-only` or `census:<Counter>`. A new route fails until it is classified, including a new field whose type is a struct already on the list (#1558): `cd server && go test ./internal/game -run TestClosureFieldsReachableFromGame -args -update-closure-fields` keeps the existing classes and marks new routes `unclassified`. The number of lines in each `census:` class and in `transient` is pinned by `closureClassCeilings` in the test and may only fall: phase 3's tiers delete lines and lower the ceiling; nothing raises one. The one exception is ADR 0041 P11: when a tier retires a counter, its lines may move to the class of the route they still have, in the same PR, and the PR lists those lines and the new ceiling.

- **CR 616 resume frames (#4253, [ADR 0013](decisions/0013-replacement-effects.md) amendment of 2026-10-23).** A "may" replacement's yes/no, riot's question and the CR 616.1 ordering prompt pause a `ReplacementEvent`. When that event holds no closure (a draw, a learn, a zone move or a single entry), the frame is written with the prompt as data (`pendingChoices[].replacementResume`: the event, the pending effects by ID, the CR 614.5 marks) and its tail key rides `pickThen`, so the table is a restore point and an older binary refuses the file. Restore gathers the event again to rebuild the effects; the object serials their IDs pack are written beside the prompts (`replacementSerials`). Every field of `ReplacementEvent` is classified in `replacementEventFields` (`game/replacement_resume_keyed.go`): a new field is a gate, keeping its frames on the closure form, until it is classified. A frame whose event holds a closure (a route's or entry's continuation, a batch, a token, life, counter, damage or mill tail) is still counted by the census. Since the amendment of 2026-10-24 the entry questions that share the frame are keyed too (`copy_target`, `entry_controller`, the four entry card choices, `aura_host`, `entry_read_ahead`, `entry_pay_life`), and so are a counter placement and a life change with no tail (`replacement-resume/counter`, `replacement-resume/life`) and a keyword action whose tail is data (`replacementResume.event.keywordActionTail`). An entry card choice's zone frame is rebuilt from its prompt kind. Since the second amendment of 2026-10-24 (slice 3) a tail can be data too: a registered continuation (`game.RegisterTail`, ledgered `tail <key>`) or an engine sequencer's own data, so the frame is keyed when its event carries a library search's remaining takes and shuffle (`entryTail.search`), a simultaneous entry (`entryTail.batch`, its settled members' events inside), a token creation (`replacement-resume/create-tokens`) or a token batch's remaining entries (`entryTail.tokens`, with the staged tokens written as `enteringTokens`), a keyed counter or life tail or a lose-life batch (`lifeTail.each`), or a face-down exile batch's next leg (`zoneRoute.faceDownLegs`). A scry or surveil prompt whose "then" is keyed is a restore point by itself (`pendingChoices[].scryThen`, its key on `pickThen`). A tail that is still a closure keeps its frame counted. Since slice 4 ([ADR 0013](decisions/0013-replacement-effects.md), the amendment headed slice 4) a keyed tail may also carry the asking stack item as data (`KeyedTail.asked`, the same `AskedItem` a keyed pay-unless prompt writes), for a card tail that reads its targets, its X or its text. Since slice 6 a tail also carries a `word` and a `next` tail, and a single permanent's return from exile or a graveyard keeps its tail on the entry (`replacementResume.event.entryTail.keyed`, under the tailed move key), so every put and return door and a token creation (amass, incubate, living weapon, Role tokens, empower Jace, a copied permanent spell) is a restore point at its entry question or order prompt. Since slice 5 (the amendment headed slice 5) the library-search prompt itself is written (`pendingChoices[].searchPrompt`: the spec's data half, whether it names a quality, its set rule by key and number, the undecided flag of a "you may search", a TakeAll search's graveyard finds), with `search-library/prompt` on `pickThen`, when its spec has no closure set rule (`SearchLibrarySpec.Rule`, a registered `searchrule <key>`, in place of `Validate`) and no closure "then". The per-card predicate is not written: it listed the candidates when the search started, the prompt carries that list, and nothing reads the predicate again.

- **Keyed prompted runs (#4290, [ADR 0041](decisions/0041-game-persistence.md) amendment of 2026-10-24).** A multi-seat instruction in flight ("each opponent discards a card", "sacrifice two lands") whose continuation is a registered key (`game.RegisterPromptRunThen`, ledger kind `run`) is written as `promptRuns` (id, outstanding, ask order, landed per seat, key, carry, source), and each leg carries `pendingChoices[].promptRun`. A keyed discard leg names `choose-cards/discard-leg` and a keyed sacrifice or permanent-pick leg names its run's key in `pickThen`, so an older binary refuses the file at the leg. A keyed permanent-pick leg's frame (the battlefield re-check and the settle) is rebuilt from the prompt. A run whose continuation is a closure is not written and is counted once by the census.
- **The rest of the prompted runs and the ordered collector (#4290, [ADR 0041](decisions/0041-game-persistence.md) amendment of 2026-10-26).** A keyed run also carries `promptRuns[].nums` and `promptRuns[].asked` (the stack item that asked it, `game.AskedItem`), so a continuation that reads the item's targets, a word of its text or the step record reads them from `RunDone.Item()`. A multi-seat `choose_cards` run's legs are keyed picks (`choose-cards/run-leg`, or a key that holds the leg's set rule), a permanent-pick leg's set rule is the one registered with the run's key, and ADR 0175's ordered collector is `pendingChoices[].ordered` (the seats still to ask, the picks so far, the registered continuation and its data). A binary that lacks a run, leg or collection key refuses the file.
- **Keyed route batches (#4253 slice 9, [ADR 0013](decisions/0013-replacement-effects.md) amendment of 2026-10-26, slice 9).** A batch of exits (an exile, a destroy, a sacrifice, a bounce, a tuck, a mill, a plain move to a graveyard) whose continuation is a registered tail carries the rest of the batch on the route of the leg now moving: `replacementResume.event.zoneRoute.batchLegs` (the leg, the cards still to route, the cards landed, the tail, and for a "mills a card, then repeats this process until …" run the run itself, its stop clause a registered key, ledgered `milluntil <key>`) and the batch's last-known copies (CR 603.10) through the card mirror, `zoneRoute.simultaneousExit`. A discard is keyed for the first time (`replacement-resume/discard`; `DiscardPlayer`, `DiscardCause`, `DiscardCauseController` are carried) with its batch on `zoneRoute.discardLegs` (the legs a replacement put on top of the library with their epochs, and the event-log mark), and a discard a replacement turned into an entry (Obstinate Baloth) carries the batch on the entry, `entryTail.batch.discard`. Each is written under a resume key of its own (`replacement-resume/move-batch`, `replacement-resume/discard`, `replacement-resume/discard-entry`), so a binary from before them refuses the file. All are additive in v9 and absent when empty; a route whose last-known copies the card mirror cannot write whole keeps its frame counted.
- **Keyed mass verbs, permissions, mill amounts and exchanges (#4253 slice 10a, [ADR 0013](decisions/0013-replacement-effects.md) amendment of 2026-10-26, slice 10a).** A keyed tail can carry a cast permission (`keyedTail.permission`, written whole as the game snapshot writes one), so an exile whose "then" grants a cast or records an "until" return is a restore point. A mill's amount window is keyed (`replacement-resume/mill`, with the tail's data half in `replacementResume.event.millTail` and `millPlayer`/`millCount` carried). An exchange's exit carries its settled entry (`replacementResume.event.zoneRoute.exchange`) under `replacement-resume/move-exchange`. A binary from before them refuses the file. All are additive in v9 and absent when empty.
